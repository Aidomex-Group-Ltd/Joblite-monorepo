## P03.01 Accounts schema, identity lookup and session token lifecycle

- Status: verified
- Behavior/result: First real migration against the empty ledger.
  `20261020164000_create_users_and_session_tokens` creates `users` (UUID PK,
  unique lowercase `email`, bcrypt `hashed_password`, optional `confirmed_at`,
  UTC timestamps) and `users_tokens` (binary `token` hash, `context`,
  `user_id` FK `on_delete: :delete_all`, `inserted_at` only, unique token
  index, user_id index). `Joblite.Accounts` is the public boundary:
  - `register_user/1` — email normalized to lowercase, format/length
    validated; password min 8/max 72; stored only as bcrypt hash
    (`Bcrypt.hash_pwd_salt`, cost 12); unique email enforced by changeset
    constraint mapped from the DB index.
  - `get_user_by_email/1` — case-normalized identity lookup, nil when absent.
  - `generate_user_session_token/1` — 32-byte `:crypto.strong_rand_bytes`
    raw token returned exactly once; only its SHA-256 hash is persisted with
    context `"session"`.
  - `get_user_by_session_token/1` — hashes the raw token, joins to user,
    rejects unknown, revoked and tokens older than 60 days
    (`@session_validity_in_days`).
  - `delete_user_session_token/1` — idempotent revocation by hash.
- Adaptation note (per atom): this is the core-only slice of `phx.gen.auth`
  patterns with every web artifact removed (no controllers, plugs, LiveViews,
  routes or `JobliteWeb` reference). Password hashing (`bcrypt_elixir 3.3.2`)
  is a core dependency; the frontend lockfile resolves it transitively through
  the sibling path dependency.
- Defects found and fixed during verification:
  1. `password` cast without a virtual field — added
     `field :password, :string, virtual: true, redact: true`.
  2. Inserts sent null UUIDs — schemas needed
     `@primary_key {:id, :binary_id, autogenerate: true}` (migration config
     alone only shapes the DDL).
  3. `belongs_to :user` inferred integer `:id` for the FK — made explicit as
     `belongs_to :user, User, type: :binary_id`.
  4. Test asserted `{:ok, _} = Bcrypt.verify_pass/2` — the API returns bare
     `true`/`false`.
  5. `assert_receive` pin (`^ref`) from P02 leftover warning fixed earlier in
     the same working tree.
- Invariant and failure case: identity uniqueness survives case-folding races
  via the DB unique index; a revoked or expired token resolves to `nil`
  (never a user); plaintext passwords and raw tokens never persist or log.
- Files and responsibilities:
  - `priv/repo/migrations/20261020164000_create_users_and_session_tokens.exs` —
    users and users_tokens DDL with UUID FK and indexes.
  - `lib/joblite/accounts/user.ex` — identity schema and registration
    changeset (normalize, validate, hash).
  - `lib/joblite/accounts/user_token.ex` — token hash schema; build, verify
    (expiry window) and delete queries; SHA-256 helper.
  - `lib/joblite/accounts.ex` — public context boundary; no web dependency.
  - `test/joblite/accounts_test.exs` — 11 tests over identity, hashing,

  - `mix.exs` — bcrypt_elixir dep; `test` alias now

## Source walkthrough

Registration: caller -> `Accounts.register_user/1` ->
`User.registration_changeset/2` (cast email/password, normalize, validate,
`Bcrypt.hash_pwd_salt`) -> `Repo.insert` -> unique index violation maps to

hashed pair, `Repo.insert` stores hash only; `get_user_by_session_token/1`

`PGPASSWORD=joblite_local_only psql -h 127.0.0.1 -p 5543 -U joblite -d joblite_test -c "SELECT context, encode(token, 'hex'), inserted_at FROM users_tokens"`
— only the SHA-256 hash appears, never a raw token.

## P03.02 Login/logout and LiveView authentication integration

- Status: verified
- Behavior/result: Core gained `Accounts.authenticate_by_email_password/2` —
  returns `{:ok, user}` or `{:error, :invalid_credentials}` for both wrong
  passwords and unknown emails; the unknown-email path still runs
  `Bcrypt.no_user_verify/0` so the two failure modes cost one bcrypt verify
  each (timing equalization against user enumeration). Web layer (all in
  `:joblite_web`, core untouched by presentation):
  - `JobliteWeb.UserAuth` — module plug (`:fetch_current_user`,
    `:redirect_if_user_is_authenticated`) plus LiveView `on_mount` hooks
    (`:mount_current_user`, `:ensure_authenticated`,
    `:redirect_if_user_is_authenticated`). `log_in_user/2` renews and clears
    the session (fixation defense) before storing the fresh raw token;
    `log_out_user/1` revokes the stored hash then renews/clears. Every
    request and every LiveView mount re-resolves the token against Accounts,
    so revocation and expiry apply to already-mounted pages on reconnect.
  - `SessionController` — `create` authenticates through the core context and
    redirects (flash on failure, no token issued); `delete` logs out.
  - `UserLoginLive` — public login form posting to `SessionController` with
    CSRF; `AccountLive` — protected page showing the server-resolved email
    with a logout form.
  - Router — `:browser` pipeline fetches the current user; live_sessions
    `:public` (login, double-guarded by plug + on_mount), `:default` (home),
    `:protected` (account, `ensure_authenticated`). App layout renders flash
    and auth-aware nav.
- Defects found and fixed during verification:
  1. Ambiguous `redirect/2` (Controller vs LiveView imports) — split imports
     and fully-qualified LiveView calls in `on_mount`.
  2. `assign_new/3` lives in `Phoenix.Component`, not `Phoenix.LiveView`.
  3. Module plug needed `init/1`.
  4. Phoenix `pipeline` generates a public router function with the pipeline's
     name — a same-named `defp` collided; the plug moved into `UserAuth`.
  5. `configure_session(renew: true)` alone does not clear in-conn session
     data — `clear_session/1` added to both login and logout.
  6. `on_mount` redirect surfaces as `{:error, {:redirect, ...}}` (not
     `live_redirect`) in tests.
- Invariant and failure case: anonymous `/account` (HTTP and connected mount)
  redirects to login; a revoked or >60-day-old token redirects on a fresh
  mount even if a prior mount succeeded; wrong password and unknown email are
  indistinguishable to the client (same flash, same status, comparable time).
- Files and responsibilities:
  - backend `lib/joblite/accounts.ex` — `authenticate_by_email_password/2`.
  - backend `test/joblite/accounts_test.exs` — 4 new auth tests (25 total).
  - frontend `lib/joblite_web/user_auth.ex` — plugs, on_mount, login/logout
    session handling.
  - frontend `lib/joblite_web/controllers/session_controller.ex` — HTTP
    login/logout actions.
  - frontend `lib/joblite_web/live/user_login_live.ex` — login form page.
  - frontend `lib/joblite_web/live/account_live.ex` — protected identity page.
  - frontend `lib/joblite_web/router.ex` — pipelines, routes, live_sessions.
  - frontend `lib/joblite_web/components/layouts/app.html.heex` — flash +
    nav.
  - frontend `test/joblite_web/session_controller_test.exs` — 6 conn tests.

## Source walkthrough (login)

Browser form POST `/users/log-in` -> `Router` `:browser` (fetch session +
CSRF + `UserAuth.fetch_current_user`) -> `SessionController.create/2` ->
`Accounts.authenticate_by_email_password/2` (normalize email, bcrypt verify
or dummy verify) -> `UserAuth.log_in_user/2` (generate raw token once, store
SHA-256 hash in DB, renew+clear session, `put_session(:user_token, raw)`)
-> redirect `/`. Subsequent request or LiveView mount: session raw token ->
`Accounts.get_user_by_session_token/1` (hash, join, expiry filter) ->
`:current_user` assign. Debugging entry point: reproduce a failed login with
`curl -d 'user[email]=x@y.z]&user[password]=wrong' http://localhost:4000/users/log-in`
and check the flash; inspect the stored token hash with
`SELECT encode(token,'hex') FROM users_tokens` — the raw value never appears
in the database or logs.
