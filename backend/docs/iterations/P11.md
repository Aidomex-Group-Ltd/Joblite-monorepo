## P11.05 Repository-root production image for the core application

- Status: verified
- Behavior/result: `backend/Dockerfile` builds the `:joblite_core` release from
  this repository alone (multi-stage: `hexpm/elixir:1.20.4-erlang-28.5.0.8-debian-bookworm-20261020-slim`
  builder, `debian:bookworm-slim` runtime, non-root uid 10001). The image
  carries the release only: no compilers, no source checkout, no Mix, no
  secret file. `mix release joblite_core` needs `releases:` in `mix.exs` and a
  production composition root, `config/runtime.exs`, which reads `DATABASE_URL`
  and the TLS policy from the environment.
- Web service or worker: **worker/service, not a web service.** This repository
  owns the Repo, the PubSub and the migration ledger; it has no router, no
  endpoint and no port. The browser-facing release (`joblite`, core + web) is
  assembled by the sibling frontend repository through `deploy/Dockerfile`
  (build context: the workspace parent). The core image therefore exposes no
  port, invents no endpoint and requires none of `PHX_HOST`, `PORT` or
  `SECRET_KEY_BASE`.
- Readiness: the image's `HEALTHCHECK` runs the core's existing bounded probe
  `Joblite.Health.readiness/1` through the release control command
  (`/app/bin/joblite_core rpc 'IO.puts(Joblite.Health.readiness() == :ok)'`).
  No HTTP route was added. `RELEASE_DISTRIBUTION=sname` is set so the control
  command can reach the running node; set `RELEASE_NODE` when several
  containers share one hostname.
- Migrations stay explicit: `docker run --rm -e DATABASE_URL=... joblite-core
  eval "Joblite.Release.migrate()"` (`Joblite.Release` is the core-owned
  helper; the product release keeps `JobliteWeb.Release.migrate/0`).
- Checks (real results on this host):
  - `docker build -t joblite-core:local-test .` — pass (image 40.8 MB,
    `Config.User=joblite`, entrypoint `/app/bin/joblite_core`, cmd `start`).
  - Boot without `DATABASE_URL` — pass as designed: exits with
    "missing required environment variable DATABASE_URL" (and
    `DATABASE_CA_CERT` when `DATABASE_SSL=verify-full` is left at its default).
  - `docker run ... eval "Joblite.Release.migrate()"` against
    `127.0.0.1:5543/joblite_dev_db` — pass ("Migrations already up").
  - Service start + readiness — pass: container reports `healthy`;
    `Joblite.Health.readiness()` returns `:ok` (query `SELECT 1` succeeds).
  - Negative case — pass: with an unreachable port the container stays up,
    logs `tcp connect ... connection refused` and the health check turns
    `unhealthy` (failing streak 5).
  - `postgresql://` URL form (the Supabase connection string shape) — pass:
    container `healthy` against the local database.
  - Secret hygiene — pass: `Application.get_env(:joblite_core, :jwt_secret)`
    is `nil` inside the image, and no `dev.env` exists in the image.
- Not verified: the supplied Supabase host was unreachable from this host
  ("Network is unreachable"; the name resolves to an IPv6 address only), so no
  connection to that database was proven. TLS against Supabase still needs a
  real run with `DATABASE_SSL=require` (no CA bundle) or `verify-full` plus
  Supabase's CA file.

## P11.06 Local development database and openssl-managed secrets

- Status: verified
- Behavior/result: the development database is `joblite_dev_db` (owner
  `joblite`, documented local-only password `joblite_local_only`,
  `127.0.0.1:5543`). The previous `joblite_dev` database was kept untouched on
  the server; `config/shared.exs` now points the `:dev` Repo at
  `joblite_dev_db`, while `:test` keeps `joblite_test`.
  `scripts/generate_secrets.sh` generates `JWT_SECRET`, `SECRET_KEY_BASE` and
  `LIVE_SIGNING_SALT` with `openssl rand -hex` into gitignored files
  (`backend/secrets/dev.env`, `frontend/secrets/dev.env`, mode 0600).
  `config/secrets.exs` loads those files into the Mix configuration for
  `:dev` only; production and test read real environment variables and the
  deterministic test values. `SECRET_KEY_BASE` and `LIVE_SIGNING_SALT` now
  reach the Phoenix endpoint from the generated file.
- Repair performed: the first generator run aborted with a bash
  "bad substitution" error (nested quoting inside a double-quoted expansion);
  the fingerprints are now computed into variables before printing.
- Checks: `scripts/generate_secrets.sh` twice — pass (identical SHA-256
  fingerprints, idempotent); `git check-ignore -v secrets/dev.env` — pass
  (ignored in both repositories, `*.example` templates tracked);
  `mix ecto.migrate` against `joblite_dev_db` — pass (migration
  `20261020164000` applied); `mix check` (backend) — pass, 25 tests;
  `mix check` (frontend) — pass, 26 tests.
