## P02.01 Create/migrate isolated development and test databases

- Status: verified
- Behavior/result: `compose.yaml` runs postgres:18 bound to `127.0.0.1:5543`,
  avoiding the host PostgreSQL 14 listener on 5432 (and other services on 5433).
  `config/shared.exs` defaults to `ecto://joblite:joblite_local_only@localhost:5543/`
  with `joblite_dev` (dev) and `joblite_test` (test); `DATABASE_URL` overrides.
  Both databases exist. `mix ecto.create` reports already-created; `mix ecto.migrate`
  reports "Migrations already up" against an empty ledger: `schema_migrations`
  exists with 0 rows (the migrations directory holds only `.gitkeep`).
- Repair performed: the previous session's postgres:18 container exited 255
  mid-crash-recovery; its Docker volume's fsync was pathologically slow
  (cumulative elapsed >220s, `./base/5/3380` unreached). Because the volume had
  never initialized (zero data, zero migrations), it was recreated with
  `docker compose down -v && up -d` and `fsync=off` added to the service command.
  `fsync=off` is safe here only because this instance is local-only (loopback
  bind, documented `joblite_local_only` password, no production or candidate
  data) and must never be copied to a shared or deployed environment. With
  `fsync=off` the cluster initialized healthy in ~4s. Evidence: `docker inspect
  backend-postgres-1` health=healthy; `ss -tlnp` shows 127.0.0.1:5543;
  `pg_isready` accepts; `SELECT datname` lists `joblite_dev`, `joblite_test`.
- Repo ownership/configuration: one Repo (`Joblite.Repo`, `:joblite_core`) reads
  `config/shared.exs`; the frontend imports the same file at compile time
  (`frontend/config/config.exs`). No production database is touched; the host
  PostgreSQL 14 was only probed to confirm the port conflict, never modified.
- Migration/data impact: none beyond empty `schema_migrations` tables. No
  application tables.
- Checks: `docker compose up` healthy — pass; `psql SELECT datname` — pass (2
  databases); `mix ecto.create` / `mix ecto.migrate` — pass (empty ledger).

## P02.02 Enable test Repo and add Sandbox helpers

- Status: verified
- Behavior/result: `start_repo: true` in `config/shared.exs` starts the Repo in
  every environment; `:test` configures `pool: Ecto.Adapters.SQL.Sandbox`.
  `test/test_helper.exs` (both repos) sets Sandbox `:manual` mode so a process
  that touches the database without ownership fails loudly instead of silently
  pooling its own connection. `Joblite.DataCase` (backend) and
  `JobliteWeb.ConnCase` (frontend) start a Sandbox owner per test
  (`shared: not tags[:async]`); DataCase exposes `allow_runner/2` for future
  worker/LiveView child processes. `mix.exs` (both) compiles `test/support` in
  the test env only.
- Tests proving isolation: `data_case_connection_test.exs` asserts
  `current_database() = joblite_test` (never `joblite_dev` or production), a
  plain `spawn`ed process without ownership receives `DBConnection.OwnershipError`,
  and `allow_runner/2` grants a child the test connection. 4 tests.
- Checks: backend `mix check` — pass (format, compile --warnings-as-errors, credo
  0 issues, 10 tests); frontend `mix check` — pass (2 tests). One test warning
  (unpinned `ref` in `assert_receive`) was found and fixed with `^ref` before
  the final run.

## P02.03 Exercise readiness and database failure behavior

- Status: verified
- Behavior/result: `Joblite.Health.readiness/1` now accepts a repo module
  (default `Joblite.Repo`) so failure mapping is testable without stopping the
  real Repo. Success: live server smoke `GET /health/ready` 200
  `{"status":"ready"}` with the database up (this endpoint correctly returned
  503 in P01 when no database existed). Failure paths:
  - missing Repo process -> `{:error, :database_unavailable}` (health_test.exs)
  - unreachable TCP port (127.0.0.1:5544, verified closed) -> the same tagged
    error via a supervised throwaway Repo (health_readiness_failure_test.exs)
  - HTTP layer maps the tagged error to 503 `{"status":"not_ready"}`
    (HealthController, unchanged since P01; 503 proven in P01, 200 proven now).
  Liveness (`GET /health/live` 200 `{"status":"up"}`) remains independent of
  the database. Frontend `home_live_test.exs` asserts both endpoints through
  ConnCase.
- Checks: backend `mix test` — 10 passed; frontend `mix test` — 2 passed;
  live curl smoke on :4000 — `/health/live` 200, `/health/ready` 200, `/` 200;
  architecture smoke `elixir scripts/check_architecture.exs` — pass in both
  repos.

start brings up `Joblite.Repo`. Test: `test_helper.exs` sets `:manual` ->

to inspect the isolated database; reproduce readiness failure by
`docker compose stop postgres` and curling `/health/ready` (expect 503), then
`docker compose start` to recover.

## Remaining risk

- `fsync=off` trades durability for speed on this local volume; acceptable only
  for the documented local-only instance. Any redeployed database must restore
  durable settings.
- No application tables or migrations exist yet; constraint/rollback conventions
  are documented but not yet exercised by a real schema migration (first
  exercise is P03.01).
- The readiness 503 HTTP path was proven in P01 (no database) and the context
  failure mapping is re-proven here with the database present but unreachable on
  a throwaway Repo; a single test that stops the real Repo and asserts HTTP 503
  was not added because Sandbox ownership makes stopping the shared Repo unsafe
  under async tests.
